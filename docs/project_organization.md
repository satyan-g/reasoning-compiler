## Git Workflow

### Branching Strategy

```
main                    ← stable, everything passes tests
├── dev                 ← integration branch, merge features here first
├── feat/frl-schema     ← FRL dataclasses + typecheck
├── feat/z3-compiler    ← FRL → Z3 compilation
├── feat/solver-runner  ← Z3 wrapper + model/core extraction
├── feat/pretokenizer   ← AMR + constraint classifier
├── feat/datagen        ← Synthetic data generation
├── feat/nl2frl-rule    ← Rule-based parser
├── feat/nl2frl-llm     ← LLM structured extraction
├── feat/eir            ← Explanation IR + checker
├── feat/search         ← Formulation-graph search
├── exp/fertility       ← Fertility measurement experiments
├── exp/baselines       ← LLM baseline runs
├── exp/ablations       ← Ablation studies
└── paper/fertility     ← Paper 1 writing
```

### Commit Convention

```
feat(frl): add FRL JSON schema with Enum, Int, Bool sorts
feat(compiler): implement FRL → Z3 Python API translation
feat(pretok): add constraint type classifier trained on synthetic data
fix(solver): handle UNSAT core extraction for tracked constraints
data(synth): generate 10k assignment puzzles with paraphrase noise
exp(fertility): measure fertility on GSM8K, correlate with GPT-4 failure
paper(fertility): draft sections 2-3, add fertility distribution figure
test(compiler): add roundtrip test FRL → Z3 → solve → verify
```

### Key Principles

1. **Every experiment is reproducible**: config file + random seed + data version = same result
2. **Data is regenerable, not committed**: scripts to generate, not the data itself
3. **Results are logged, not committed**: use results/ dir locally, export tables/figures to papers/
4. **Tests gate merges**: no merge to dev without passing tests for affected modules

## Experiments

### EXP-01: Fertility Baseline (Paper 1, Section 3)

**Question**: Does formalization fertility correlate with LLM reasoning failure?

**Setup**:
- Datasets: GSM8K (200 problems), logic grid puzzles (50), assignment puzzles synthetic (200)
- Manual annotation: for each problem, count entities, constraints, quantifiers, implicit assumptions
- Token counting: tiktoken (GPT-4 tokenizer), sentencepiece (Llama tokenizer)
- LLM evaluation: run GPT-4, Claude, Llama-3-70B on each problem, record correct/incorrect

**Metrics**:
| Metric | Definition |
|--------|-----------|
| fertility_basic | NL_tokens / num_constraints |
| fertility_entity | NL_tokens / num_entities |
| constraint_density | num_constraints / num_sentences |
| implicit_ratio | implicit_constraints / total_constraints |
| quantifier_complexity | num_quantifier_phrases / num_constraints |

**Analysis**:
- Pearson/Spearman correlation: fertility vs. LLM accuracy
- Logistic regression: predict LLM failure from fertility features
- Stratified analysis: easy (low fertility) vs. hard (high fertility) problems
- Cross-dataset: does the correlation hold across GSM8K, logic grids, synthetic?

**Expected output**: 
- Figure: scatter plot, fertility (x) vs. LLM accuracy (y), with regression line
- Figure: fertility distribution, colored by success/failure
- Table: correlation coefficients per dataset × model
- Statistical tests: p-values for correlation significance

**Estimated time**: 1 week (annotation is the bottleneck)

### EXP-02: AMR/DRS as Pre-Tokenizer Baseline (Paper 1, Section 4)

**Question**: Does AMR parsing recover entities and constraints from problem text?

**Setup**:
- Parse all annotated problems with amrlib
- Parse a subset (50) with DRS tools (Parallel Meaning Bank)
- Map AMR nodes → FRL entities, AMR relations → FRL constraints
- Measure coverage: what % of gold entities/constraints appear in AMR output?

**Metrics**:
| Metric | Definition |
|--------|-----------|
| entity_recall | gold_entities_found_in_AMR / total_gold_entities |
| entity_precision | AMR_nodes_that_map_to_entities / total_AMR_nodes |
| constraint_recall | gold_constraints_recoverable_from_AMR / total_gold_constraints |
| quantifier_accuracy | correctly_parsed_quantifiers / total_quantifiers |

**Analysis**:
- Where does AMR succeed? (entity extraction, simple relations)
- Where does AMR fail? (implicit constraints, complex quantifiers, AllDifferent)
- DRS vs AMR: does DRS handle quantifiers/negation better?
- Gap analysis: what the constraint classifier needs to add on top of AMR

**Expected output**:
- Table: recall/precision for entities and constraints, AMR vs DRS
- Error taxonomy: categorize AMR failures by type
- This directly motivates the constraint classifier (next experiment)

**Estimated time**: 3-4 days

### EXP-03: Constraint Pre-Tokenizer (Paper 1, Section 4-5)

**Question**: Does constraint pre-tokenization reduce fertility and improve downstream formalization?

**Setup**:
- Train constraint type classifier on synthetic data (10k examples)
- Build full pipeline: AMR → entity extraction → constraint classification → quantifier normalization → structured IR
- Run on: synthetic test set (1k), annotated real problems (50+)

**Sub-experiments**:

#### 3a: Classifier accuracy
| Config | Training data | Test data | Model |
|--------|--------------|-----------|-------|
| 3a-rule | — | synthetic 1k | regex + dep parse |
| 3a-bert | synthetic 10k | synthetic 1k | DeBERTa-v3-base |
| 3a-bert-real | synthetic 10k | annotated real 50 | DeBERTa-v3-base |
| 3a-llm | — (few-shot) | annotated real 50 | GPT-4 structured |

Metrics: per-class F1 for each constraint type (EXCLUSION, CONDITIONAL, CARDINALITY, etc.)

#### 3b: Fertility reduction
| Config | Pipeline | Measured on |
|--------|----------|-------------|
| 3b-raw | raw NL tokens | all problems |
| 3b-amr | AMR only | all problems |
| 3b-pretok | full pre-tokenizer | all problems |

Metrics: fertility_basic before and after, fertility reduction ratio

#### 3c: Downstream formalization accuracy
| Config | NL2FRL method | Input |
|--------|--------------|-------|
| 3c-raw | LLM structured extraction | raw NL |
| 3c-pretok | LLM structured extraction | pre-tokenized IR |
| 3c-pretok-repair | LLM extraction + Z3 repair | pre-tokenized IR |

Metrics: FRL exact match, FRL equivalence (same solution set), solve@1, solve@5

**Expected output**:
- Table: classifier F1 per class across configs
- Table: fertility before/after pre-tokenization
- Table: formalization accuracy with/without pre-tokenizer
- Figure: ablation ladder showing each component's contribution

**Estimated time**: 2 weeks

### EXP-04: Full Pipeline vs. Baselines (Paper 1, Section 5)

**Question**: Does the full system (pre-tokenizer + FRL + solver) beat LLM one-shot?

**Setup**:
- Evaluate on: synthetic test (500), GSM8K subset (200), logic grids (50)
- Multiple problem difficulty levels

**Configs**:
| System | Description |
|--------|-------------|
| LLM-oneshot | GPT-4 direct answer |
| LLM-CoT | GPT-4 chain-of-thought |
| LLM-PAL | GPT-4 → Python program |
| LLM-DECL | GPT-4 → equations + sympy (He et al. 2023) |
| LLM→Z3-direct | GPT-4 → Z3 code directly (no FRL) |
| OURS-K1 | pre-tokenizer → FRL → Z3 (single attempt) |
| OURS-K5 | pre-tokenizer → FRL → Z3 (5 candidates + repair) |
| OURS-K10 | pre-tokenizer → FRL → Z3 (10 candidates + repair) |

**Metrics**:
| Metric | What it measures |
|--------|-----------------|
| solve@1 | % correct on first attempt |
| solve@K | % correct within K attempts |
| verified_rate | % where answer has a certificate |
| avg_tokens | average tokens consumed (input + output) |
| robustness_gap | accuracy drop from clean → paraphrased |

**Expected output**:
- Table: all systems × datasets × metrics
- Figure: solve rate vs. number of candidates K (showing diminishing returns)
- Figure: robustness comparison (clean vs. paraphrase vs. distractor)

**Estimated time**: 1 week (mostly API calls)

### EXP-05: Robustness Tests (Paper 1, Section 5)

**Question**: Which systems are robust to surface perturbations that don't change the problem?

**Perturbation types** (applied to synthetic + real problems):

| Perturbation | Description | Expected effect on fertility |
|-------------|-------------|------------------------------|
| paraphrase | Reword constraints ("cannot" → "is unable to") | Unchanged |
| reorder | Shuffle sentence order | Unchanged |
| distractor | Add 1-3 irrelevant sentences | Increases |
| quantifier_rephrase | "at least 3" → "no fewer than 3" | Unchanged |
| negation_scope | "not both A and B" → "A or B but not both" | Unchanged |
| name_change | Replace Alice→Diana, Bob→Eric | Unchanged |

**Configs**: run all systems from EXP-04 on each perturbation type

**Metrics**:
| Metric | Definition |
|--------|-----------|
| accuracy_clean | baseline accuracy |
| accuracy_perturbed | accuracy after perturbation |
| robustness_gap | accuracy_clean - accuracy_perturbed |
| worst_case_gap | max gap across perturbation types |

**Expected output**:
- Table: accuracy per system × perturbation type
- Key finding: pre-tokenizer should stabilize performance under paraphrase/reorder/distractor because it extracts structure before surface variation hits

**Estimated time**: 3-4 days

### EXP-06: Runtime Search + Explanations (Paper 2)

**Question**: Does formulation-graph search with backtracking improve over K-independent attempts?

**Setup**: 
- Compare K-independent (sample K FRLs, try each) vs. search (repair failed FRLs using error signal)
- Evaluate explanation faithfulness

**Configs**:
| System | Search | ASK | EIR |
|--------|--------|-----|-----|
| K-independent | No | No | No |
| search-no-ask | Yes (error repair) | No | No |
| search-ask | Yes | Yes | No |
| search-ask-eir | Yes | Yes | Yes |

**Metrics** (in addition to solve rate):
| Metric | Definition |
|--------|-----------|
| solver_calls | average Z3 calls per problem |
| questions_asked | average clarifying questions (ASK) |
| eir_pass_rate | % explanation steps that pass checker |
| constraint_coverage | % constraints cited in explanation |
| explanation_length | average EIR steps |

**Expected output**:
- Table: search vs. independent, showing efficiency gains
- Figure: solve rate vs. solver calls (search converges faster)
- Table: explanation quality metrics
- Case study: 3 worked examples showing search + ASK + EIR

**Estimated time**: 2 weeks

### EXP-07: Error Analysis (Both papers)

**Question**: Where does each component fail, and what's the bottleneck?

**Method**: On all problems that the full system fails to solve:
1. Categorize the failure stage: entity extraction / constraint classification / quantifier parsing / FRL assembly / solver (UNSAT when should be SAT) / wrong answer
2. For each failure, identify root cause
3. Compute: % failures at each stage

**Error taxonomy**:
| Error type | Stage | Example |
|-----------|-------|---------|
| missed_entity | pre-tokenizer | Didn't identify "the third machine" as an entity |
| wrong_constraint_type | classifier | Classified CONDITIONAL as EXCLUSION |
| quantifier_error | normalizer | "at most 2" parsed as "exactly 2" |
| implicit_miss | pre-tokenizer | Missed that "each person" implies AllDifferent |
| assembly_error | FRL | Valid extractions but wrong FRL structure |
| solver_timeout | runtime | Z3 didn't terminate in time limit |
| wrong_domain | routing | Problem needed optimization, tried SAT |

**Expected output**:
- Pie chart: failure distribution by stage
- Table: error types with frequency and examples
- Key insight: which stage to improve next

**Estimated time**: 3-4 days (manual inspection of ~100 failures)

## Logging and Tracking

### Per-problem output (JSONL)

Every run produces a JSONL file where each line is one problem:

```json
{
  "problem_id": "gsm8k_0042",
  "nl_text": "Alice, Bob...",
  "system": "OURS-K5",
  "attempts": [
    {
      "k": 1,
      "frl": { ... },
      "typecheck_ok": true,
      "solver_result": "SAT",
      "witness": {"assign_Alice": "Paint", ...},
      "verified": true,
      "correct": true
    }
  ],
  "final_answer": "Alice=Paint, Bob=Pack, Cara=Weld",
  "correct": true,
  "tokens_used": 847,
  "solver_calls": 2,
  "fertility_before": 12.3,
  "fertility_after": 3.1,
  "wall_time_s": 2.4
}
```

### Aggregate tracking

Use a simple CSV or SQLite database that accumulates across runs:

```
run_id, experiment, system, dataset, n_problems, solve_at_1, solve_at_5, verified_rate, avg_tokens, timestamp
```

This makes it trivial to generate comparison tables for the paper.
